1. Project Overview & Statement

Standard SOC educational projects usually stop at threat detection, neglecting the complete incident response lifecycle. Project SIREN builds a fully interactive Mini-SOC environment, simulating raw log management (Module 1), SIEM detection rules (Module 2), proactive behavioral profiling (Module 3), and incident response containment with compliance reporting (Module 4).

The client-side dashboard mimics real Splunk-style monitoring, allowing security analysts to investigate detailed event timelines, assess threat severities dynamically via risk-scoring algorithms ($Likelihood \times Impact$), run simulated firewall blocks, and output audit-ready report logs aligning with the NIST Incident Response Lifecycle (SP 800-61).

2. Security Tool Stack & Roles

During live deployment (Stage 9), SIREN coordinates several tools to create a realistic environment:

Kali Linux Attacker node. Simulates password spraying and port discovery scans. Hydra, Medusa, Nmap.

3. SIEM Correlation Rules & SPL Specifications

SIREN evaluates logs against three primary detection rules modeled directly on Splunk Search Processing Language (SPL):

Rule 1: SSH Brute Force Detection (MITRE ATT&CK: T1110)

Triggers when an IP generates $\ge 5$ failed password attempts inside a 2-minute time window.

index=linux_logs sourcetype=linux_secure "Failed password"
| rex field=_raw "Failed password for (invalid user )?(?<user>\S+) from (?<src_ip>\S+)"
| bucket _time span=2m
| stats count as failed_attempts, min(_time) as first_attempt, max(_time) as last_attempt by src_ip, user, _time
| where failed_attempts >= 5
| eval likelihood=case(
    failed_attempts<=2, 1, failed_attempts<=4, 2,
    failed_attempts<=9, 3, failed_attempts<=20, 4,
    failed_attempts>20, 5)
| eval impact=if(user="root" OR user="admin", 5, 3)
| eval risk_score=likelihood*impact
| eval severity=case(
    risk_score<=6, "Low", risk_score<=12, "Medium",
    risk_score<=19, "High", risk_score>=20, "Critical")
| eval mitre_technique="T1110 - Brute Force"
| table first_attempt, last_attempt, src_ip, user, failed_attempts, likelihood, impact, risk_score, severity, mitre_technique
| sort -risk_score

Rule 2: Firewall Port Scan Detection (MITRE ATT&CK: T1046)

Triggers when a source IP contacts $\ge 5$ unique ports within a 1-minute window.

index=linux_logs sourcetype=linux_secure OR sourcetype=firewall_logs
| bucket _time span=1m
| stats dc(dest_port) as unique_ports, values(dest_port) as ports_hit by src_ip, _time
| where unique_ports >= 5
| eval likelihood=case(
    unique_ports<=6, 3, unique_ports<=10, 4, unique_ports>10, 5)
| eval impact=3
| eval risk_score=likelihood*impact
| eval severity=case(
    risk_score<=6, "Low", risk_score<=12, "Medium",
    risk_score<=19, "High", risk_score>=20, "Critical")
| eval mitre_technique="T1046 - Network Service Discovery"
| table _time, src_ip, unique_ports, ports_hit, risk_score, severity, mitre_technique
| sort -risk_score

4. Proactive Anomaly Detection Mechanics

Rather than relying solely on event thresholds, SIREN uses behavioral analysis elements to adjust severity:

  • Time-of-Day Anomaly (Off-Hours Bump): Attack attempts launched during off-hours (defined as before 8:00 AM or after 8:00 PM) represent a higher anomaly score. The system automatically increases the Likelihood rating by +1 (up to a max of 5), increasing the final Risk Score.
  • Target Account Impact Escalation: SSH authentication attempts targeting critical infrastructure credentials (like the default accounts root or admin) represent higher target value. The impact rating is set to 5 (instead of 3 for normal users).
  • Compromise Detection (Critical Escalation): A successful login event (Accepted password) originating from the same IP address and username within the brute force window escalates the alert severity instantly to CRITICAL, overriding normal risk scores to flag active host compromise.

5. Incident Response Workflow & Playbook

Analysts follow the standard NIST response procedures supported interactively by the dashboard:

  1. Detection & Analysis: Alerts trigger dynamically based on raw logs. The analyst evaluates the threat severity cards and selects a threat to investigate.
  2. Timeline Investigation: The console compiles a clean timeline showing only the related attacker events. The system tracks Time to Detect (MTTD) based on log boundaries.
  3. Analyst-Confirmed Containment: The analyst runs the containment script. A confirmation prompt prevents unauthorized or autonomous host blocks.
  4. Eradication & Audit Reporting: The dashboard executes the IP drop command in a mock console window, updates the status to Contained, tracks Time to Respond (MTTR), and generates an official incident report file.

6. Automation Containment Script Code

The following script, incident_response.sh, is written in Bash and deployed to target hosts to handle containment:

#!/bin/bash
# incident_response.sh
# Usage: ./incident_response.sh <attacker_ip> <failed_attempts> <target_user> <attack_hour(0-23)>

ATTACKER_IP=$1
ATTEMPTS=$2
TARGET_USER=$3
ATTACK_HOUR=$4
TIMESTAMP=$(date '+%Y-%m-%d %H:%M:%S')
INCIDENT_ID="INC-$(date +%s)"

if [ -z "$ATTACKER_IP" ] || [ -z "$ATTEMPTS" ] || [ -z "$TARGET_USER" ]; then
  echo "Usage: $0 <attacker_ip> <failed_attempts> <target_user> <attack_hour(0-23)>"
  exit 1
fi

# --- Likelihood scoring (attempt volume) ---
if [ "$ATTEMPTS" -le 2 ]; then LIKELIHOOD=1
elif [ "$ATTEMPTS" -le 4 ]; then LIKELIHOOD=2
elif [ "$ATTEMPTS" -le 9 ]; then LIKELIHOOD=3
elif [ "$ATTEMPTS" -le 20 ]; then LIKELIHOOD=4
else LIKELIHOOD=5
fi

# --- Time-of-day anomaly bump (Proactive Detection) ---
if [ -n "$ATTACK_HOUR" ] && { [ "$ATTACK_HOUR" -lt 8 ] || [ "$ATTACK_HOUR" -ge 20 ]; }; then
  if [ "$LIKELIHOOD" -lt 5 ]; then LIKELIHOOD=$((LIKELIHOOD + 1)); fi
  TIME_FLAG="Unusual login time (off-hours) - likelihood increased"
else
  TIME_FLAG="Normal login time window"
fi

# --- Impact scoring (account sensitivity) ---
if [ "$TARGET_USER" == "root" ] || [ "$TARGET_USER" == "admin" ]; then
  IMPACT=5
else
  IMPACT=3
fi

RISK_SCORE=$((LIKELIHOOD * IMPACT))

if [ "$RISK_SCORE" -le 6 ]; then SEVERITY="Low"
elif [ "$RISK_SCORE" -le 12 ]; then SEVERITY="Medium"
elif [ "$RISK_SCORE" -le 19 ]; then SEVERITY="High"
else SEVERITY="Critical"
fi

echo "=== SOC ALERT ==="
echo "Incident ID: $INCIDENT_ID"
echo "Source IP: $ATTACKER_IP"
echo "Failed Attempts: $ATTEMPTS"
echo "Time Flag: $TIME_FLAG"
echo "Risk Score: $RISK_SCORE ($SEVERITY)"
echo "MITRE ATT&CK: T1110 - Brute Force"
echo "=================="

# --- Containment: analyst-confirmed, not autonomous ---
read -p "Confirm containment: block $ATTACKER_IP? (y/n): " CONFIRM
if [ "$CONFIRM" == "y" ]; then
  sudo iptables -A INPUT -s "$ATTACKER_IP" -j DROP
  ACTION="IP $ATTACKER_IP blocked via iptables (analyst-confirmed)"
  echo "$ACTION"
else
  ACTION="No containment action taken (analyst declined)"
fi

# --- Report generation ---
REPORT_FILE="incident_report_${INCIDENT_ID}.txt"
cat <<EOF > "$REPORT_FILE"
INCIDENT REPORT
================
Incident ID: $INCIDENT_ID
Detection Time: $TIMESTAMP
Attack Type: SSH Brute Force
MITRE ATT&CK Technique: T1110 - Brute Force
Source IP: $ATTACKER_IP
Target Account: $TARGET_USER
Failed Attempts: $ATTEMPTS
Time Analysis: $TIME_FLAG
Risk Score: $RISK_SCORE
Severity: $SEVERITY
Response Action: $ACTION
Response Type: Semi-automated (Splunk detects, analyst confirms containment)
Framework Followed: NIST IR Lifecycle
Final Status: $( [ "$CONFIRM" == "y" ] && echo "Contained" || echo "Under Review" )

--- Known Limitations (for transparency) ---
- Detection window is fixed at 2 minutes; attacks spanning window
  boundaries may undercount.
- Containment requires analyst confirmation (not fully autonomous).
EOF

echo "Incident report saved: $REPORT_FILE"

8. Deployment & Hosting Manual

Deploying to Vercel (Using GitHub Sync)

Vercel integrates directly with GitHub, enabling automatic deployments upon every code push:

  1. Navigate to **[https://vercel.com/new](https://vercel.com/new)**.
  2. Log in using your GitHub account.
  3. In the list of repositories, locate siren-soc-demo and click Import.
  4. Leave the default settings unchanged and click Deploy.
  5. Vercel will build the project and provide a public HTTPS URL (e.g., siren-soc-demo.vercel.app).

Deploying to GitHub Pages

If you prefer hosting directly on GitHub, configure GitHub Pages in settings:

  1. Go to your repository settings page: github.com/25211a05ee-bhargav/siren-soc-demo/settings/pages
  2. Under Build and deployment > Source, choose Deploy from a branch.
  3. Select the branch main and folder / (root), then click **Save**.
  4. Wait 60 seconds, and the site will load at: https://25211a05ee-bhargav.github.io/siren-soc-demo/
